# doc-extractor

CLI, который получает текст документа (счёт, коммерческое предложение, акт) и возвращает JSON по фиксированной схеме.
Главный принцип: **чего нет в тексте — то `null`**. Модели не верим на слово: каждое значение,
которое она вернула, проверяется детерминированным кодом по исходному тексту.

Модель — локальная, через [Ollama](https://ollama.com) (по умолчанию `gemma3:4b`). Платный API не нужен.
Вызов LLM в пайплайне и в eval настоящий; заглушка (`ScriptedLLM`) используется только в unit-тестах.

## Запуск с нуля

Нужно: Python 3.10+, Ollama, ~3,5 ГБ на диске под модель.

```bash
# 1. Модель
ollama pull gemma3:4b           # Ollama должна быть запущена (приложение или `ollama serve`)

# 2. Код
git clone <URL этого репозитория> doc-extractor
cd doc-extractor
python3 -m venv .venv
source .venv/bin/activate       # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# 3. Тесты (Ollama не нужна)
python -m pytest -q

# 4. Eval на всём наборе (11 документов, нужна Ollama)
python eval.py                  # или: make eval

# 5. Один документ
python -m extractor data/docs/01_invoice_given.txt
cat data/docs/02_offer_given.txt | python -m extractor   # Windows cmd: type data\docs\02_offer_given.txt | python -m extractor
```

Если есть `make`: `make setup && make test && make eval`.

Переменные окружения (необязательные):

| Переменная     | По умолчанию             | Что задаёт            |
|----------------|--------------------------|-----------------------|
| `OLLAMA_MODEL` | `gemma3:4b`              | модель Ollama         |
| `OLLAMA_HOST`  | `http://localhost:11434` | адрес сервера Ollama  |

Другую модель можно передать и флагом: `python eval.py --model qwen2.5:7b` (её нужно сначала скачать через `ollama pull`).

Коды выхода CLI: `0` — успех; `1` — модель так и не дала валидный ответ (выдан безопасный пустой результат);
`2` — Ollama недоступна или пустой/нечитаемый вход.

## Как устроено

```
текст ──► LLM (Ollama, temperature=0, JSON-схема в format)
            │
            ▼
      json.loads + pydantic LLMExtraction (типы, enum, запрет лишних полей)
            │ не прошло ──► ошибки отправляются модели, 1 повтор
            │               не прошло снова ──► пустой результат + LLM_OUTPUT_INVALID, exit 1
            ▼
      grounding (postprocess.py): каждое поле ищется в исходном тексте
            │ не нашлось ──► null + UNGROUNDED_DROPPED в warnings
            ▼
      проверки согласованности (checks.py) ──► warnings
            ▼
      pydantic ExtractionResult (БИН = 12 цифр, дата ISO, confidence ∈ [0,1]) ──► JSON
```

| Файл | Что делает |
|------|-----------|
| `extractor/schema.py` | pydantic-схемы: сырой ответ модели и финальный результат |
| `extractor/prompt.py` | системный промпт с правилами заполнения полей |
| `extractor/llm.py` | клиент Ollama и тестовая заглушка |
| `extractor/pipeline.py` | оркестрация: вызов → валидация → повтор → fallback |
| `extractor/normalize.py` | числа цифрами и прописью (рус/каз), даты (рус/каз), БИН + контрольная сумма, OCR-исправления |
| `extractor/postprocess.py` | grounding каждого поля и расчёт `field_confidence` |
| `extractor/checks.py` | противоречия: две суммы, две даты, сумма позиций ≠ итог, НДС не облагается |
| `extractor/metrics.py` | сравнение с эталоном: верно / неверно / галлюцинация / пропуск |
| `eval.py` | прогон набора и отчёт |

### Что происходит с невалидным ответом модели

1. Ответ модели — это просто строка. Сначала `json.loads`, потом `LLMExtraction.model_validate`:
   неверный `doc_type`, строка вместо числа, лишнее поле (`extra="forbid"`) — всё это ошибка.
2. Ошибки pydantic в кратком виде уходят модели вторым сообщением: «исправь и верни JSON». Максимум 1 повтор.
   Если повтор помог — в `warnings` будет `LLM_OUTPUT_REPAIRED`.
3. Если и повтор невалиден — клиент получает **безопасный пустой результат** (`doc_type: unknown`, все поля `null`,
   `warnings: ["LLM_OUTPUT_INVALID: ...текст ошибок..."]`), CLI выходит с кодом 1. Невалидные данные наружу не уходят.
4. После пост-обработки результат ещё раз валидируется финальной схемой — даже ошибка в нашем коде не даст отдать
   «БИН» из 11 цифр или дату `12.11.2026`.

Это покрыто тестами в `tests/test_pipeline.py`.

### field_confidence

Самооценке модели не доверяем. Confidence считается по тому, **как значение подтвердилось в тексте**:

| Значение | Когда |
|---------:|-------|
| 0.95 | найдено в тексте как есть |
| 0.75 | найдено после нормализации: OCR-исправление (`2l064090Ol80`), сумма прописью, латиница вместо кириллицы |
| 0.5  | найдено, но есть сомнение: БИН не проходит контрольную сумму; в тексте нет ключевых слов для `doc_type` |
| 0.0  | поле `null` |

Confidence выдаётся для всех скалярных полей. Для `line_items` отдельной оценки нет — каждая позиция проходит grounding,
непрошедшие отбрасываются с предупреждением.

## Правила заполнения полей (принятые решения)

ТЗ местами неоднозначно; ниже — как я его истолковал. Эти же правила написаны в промпте.

**Общее.** Значение попадает в ответ, только если оно найдено в тексте (цифрами, прописью или с OCR-ошибкой).
Не найдено — `null` и предупреждение `UNGROUNDED_DROPPED`. Мы сознательно меняем галлюцинацию на пропуск: пропуск видно, а
выдуманный БИН уходит в учёт молча.

| Поле | Правило |
|------|---------|
| `doc_type` | счёт на оплату / счёт-фактура / шот-фактура / invoice → `invoice`; КП → `commercial_offer`; акт → `act`; иначе `unknown`. «Шот-фактура № AKT-09» (док. 3) — `invoice`: тип определяем по названию документа, а не по префиксу номера. |
| `unknown` | Если тип `unknown` (письмо, договор), **все остальные поля очищаются**: реквизиты в письме могут быть чьими угодно (в док. 10 это реквизиты покупателя). Предупреждение `DOC_TYPE_UNKNOWN_FIELDS_CLEARED`. |
| `supplier_name` | Продавец/исполнитель, как написано (с ТОО/ИП/ЖШС). Если название на двух языках — русский вариант. Eval принимает оба. |
| `supplier_bin` | Только БИН поставщика. Если БИН стоит в строке после «Заказчик/Покупатель» — отбрасывается. OCR-путаница `O→0`, `l→1` исправляется (`BIN_OCR_CORRECTED`, confidence 0.75) — это не выдумывание: цифры есть в документе, просто распознаны криво. Контрольная сумма не сходится — **значение оставляем** (оно есть в документе), но пишем `BIN_CHECKSUM_FAILED` и confidence 0.5. Так в док. 1 из ТЗ: `170340021554` не проходит проверку контрольного разряда. |
| `doc_number` | Номер самого документа без `№`. Номер договора не берём. |
| `doc_date` | Дата документа в ISO. Несколько дат → дата в заголовке рядом с номером. Срок действия КП, дата договора, дата подписи — не дата документа. Поддерживаются `12.11.2026`, `2 ноября 2026`, `09 қазан 2026`. |
| `currency` | Только если валюта названа: тенге/теңге/тг/₸ → KZT, USD/$/доллар → USD, EUR/€/евро → EUR. Валюты нет — `null` (не «KZT по умолчанию»). |
| `total_amount` | Итог к оплате (с НДС). Есть «Итого» и «Всего к оплате» → берём «к оплате». Сумма прописью считается (`Үш жүз қырық мың` = 340000). Итога нет — `null`, сами не суммируем (док. 2). |
| `vat_amount` | Только если сумма НДС написана. «НДС не облагается», «Без НДС» → `null` + `VAT_EXEMPT`. «Цены с учётом НДС» без суммы → `null` + `VAT_INCLUDED_NOT_STATED`. Почему не `0`: в схеме `null` = «в документе нет числа», а 0 было бы нашим выводом. |
| `line_items` | `price` — цена за единицу (не сумма строки). Количество не указано — `qty: null`, а не 1. Позиция, которой нет в тексте, отбрасывается. |

### Противоречия → warnings

| Код | Когда | Как заполняется поле |
|-----|-------|----------------------|
| `TOTALS_CONFLICT` | две разные итоговые суммы, и разница не объясняется НДС | `total_amount` из строки «к оплате», иначе — последняя итоговая |
| `DATES_CONFLICT` | несколько дат с метками «от», «дата», «№» | `doc_date` — дата в заголовке рядом с номером |
| `ITEMS_SUM_MISMATCH` | Σ qty×price ≠ итог (и ≠ итог − НДС) | ничего не меняем |
| `BIN_CHECKSUM_FAILED`, `BIN_OCR_CORRECTED` | см. выше | — |
| `VAT_EXEMPT`, `VAT_INCLUDED_NOT_STATED` | см. выше | `vat_amount = null` |
| `UNGROUNDED_DROPPED` | значение модели не найдено в тексте | поле → `null` |
| `LLM: ...` | противоречие, которое заметила сама модель | — |

Противоречия ищутся **кодом**, независимо от модели: если модель промолчит, предупреждение всё равно будет.

## Тестовый набор

`data/docs/*.txt` — документы, `data/expected/*.json` — эталоны. В эталоне строковое поле может быть списком
допустимых вариантов (двуязычное название, `507` / `5O7`). `expected_warnings` — коды предупреждений, которые
система обязана выдать. `_note` — пояснение, что проверяет документ.

| # | Документ | Что проверяет |
|---|----------|---------------|
| 01 | счёт из ТЗ | базовый случай; «Итого» vs «Всего к оплате»; БИН не проходит контрольную сумму |
| 02 | КП из ТЗ | нет БИН, номера, итога; две даты (срок действия ≠ дата документа); qty не указано |
| 03 | шот-фактура из ТЗ | каз/рус, OCR в БИН, сумма прописью по-казахски, «НДС не облагается» |
| 04 | акт | **два БИН** — второй принадлежит заказчику; НДС «в т.ч.» с копейками |
| 05 | счёт USD | **итог только прописью** по-русски, дата словами, «Без НДС» |
| 06 | счёт с OCR-шумом | **латиница вперемешку с кириллицей**, `O` вместо `0` в БИН, номере, дате |
| 07 | счёт ИП | **нет БИН, номера, даты и валюты** — ловушка на галлюцинации |
| 08 | счёт с противоречиями | **два разных итога и две даты** |
| 09 | акт каз/рус, EUR | **смешанный казахско-русский текст**, исполнитель vs заказчик, ҚҚС-сыз |
| 10 | письмо покупателя | **не документ**: всё `null`, хотя есть БИН, сумма, номер и дата договора |
| 11 | КП | «цены с учётом НДС» без суммы — **модель не должна посчитать 16% сама** |

## Eval

```bash
python eval.py            # все документы
python eval.py --only 08  # один документ
```

Печатает для каждого поля: точность, число неверных значений, **галлюцинаций** (заполнено, а в эталоне `null`)
и **пропусков** (`null`, а в эталоне значение) — раздельно. Плюс: совпадение позиций (лишние / пропущенные),
найдены ли ожидаемые предупреждения, сколько ответов модели не прошли валидацию и сколько значений отбросил grounding.
Список всех расхождений — в конце отчёта. Предсказания сохраняются в `out/predictions/`, отчёт — в `out/eval_report.json`.

Для `doc_type` значение `unknown` считается «пустым» (как `null`); для `line_items` — пустой список.

### Результаты

Модель `gemma3:4b` через Ollama, ноутбук с NVIDIA GeForce RTX 3050 Ti и 16 ГБ RAM. 11 документов, 159 с (14,5 с на документ).

```
поле            точность  верно  неверно  галлюц.  пропуск
doc_type             91%     10        0        1        0
supplier_name        82%      9        1        1        0
supplier_bin         91%     10        0        1        0
doc_number           91%     10        0        1        0
doc_date             91%     10        0        1        0
currency             91%     10        0        1        0
total_amount         64%      7        0        0        4
vat_amount          100%     11        0        0        0
line_items           82%      9        2        0        0
ИТОГО                87%     86        3        6        4

Галлюцинации (заполнено, а в эталоне null): 6
Пропуски (null, а в эталоне есть значение):  4
Неверные значения (оба заполнены, не равны): 3
Позиции: совпало 13/16, лишних (выдуманных) 3, пропущено 3
Ожидаемые предупреждения найдены: 8/8
Ответов модели, не прошедших валидацию: 0 (исправлено повтором: 0)
Значений модели, отброшенных grounding-проверкой (не найдены в тексте): 2
```

Разбор:
- **Все 6 галлюцинаций — из одного документа** (10, письмо покупателя). Модель определила его как `invoice` и заполнила
  реквизиты покупателя: название, БИН, номер и дату договора, валюту. Grounding их не отбросил — все значения действительно
  есть в тексте. Это известное ограничение: проверяется наличие значения, а не его роль. Правило очистки для `unknown`
  не сработало, потому что тип определён неверно. На остальных 10 документах галлюцинаций 0.
- **НДС ни разу не вычислен моделью** (`vat_amount` 100%), включая ловушку «цены с учётом НДС» в документе 11.
- **`total_amount` — худшее поле (64%), все 4 ошибки — пропуски** (документы 04, 07, 08, 11). При неоднозначности
  (НДС рядом с итогом, два разных итога, не указана валюта) модель оставляет поле пустым. Строгий промпт на маленькой
  модели сдвигает ошибки в сторону пропусков.
- В документе 07 у позиций пропали цены (`price: null`), поэтому позиции засчитаны как неверные.
- Двуязычные названия (документ 03) модель возвращает целиком через `/`, вопреки правилу промпта «бери русский вариант»:
  засчитано как неверное и для поставщика, и для позиции.
- Противоречия (две суммы, две даты) в документе 08 модель не отметила сама, их нашёл `checks.py`.

Промпт после этого прогона не менялся: правка на тех же 11 документах была бы подгонкой под тестовый набор.

## Что сделано / что нет

Сделано:
- CLI + пайплайн с двухуровневой валидацией pydantic, повтором с обратной связью и безопасным fallback;
- grounding всех полей и позиций, confidence по правилам;
- разбор сумм прописью (рус/каз), дат (рус/каз), БИН с контрольной суммой и OCR-исправлением;
- детерминированный поиск противоречий;
- 11 документов с эталонами (8 своих, из них 7 сложных), eval с раздельным подсчётом галлюцинаций и пропусков;
- 36 unit-тестов, работают без Ollama.

Не сделано / ограничения:
- Grounding чисел слабый для маленьких значений: `qty = 1` «подтвердится», если в тексте есть любая единица.
  Правильнее искать число рядом с названием позиции.
- Grounding проверяет, что значение **есть** в тексте, но не что оно **в нужном месте**: если модель возьмёт
  номер договора вместо номера счёта, это не поймается (кроме БИН заказчика — для него есть проверка роли).
- Нет HTTP-сервиса — только CLI (ТЗ разрешает «сервис или CLI»).
- Набор из 11 документов мал для статистических выводов; точность ±10 п.п. — это шум.
- Прописью поддержаны только целые суммы (тиыны/копейки прописью не разбираются).
- Тип документа проверяется только по наличию ключевого слова в тексте. Письмо со словами «выставить счёт на оплату»
  проходит как счёт (документ 10 в eval) — нужна проверка по заголовку документа.

Что сделал бы дальше: см. `REFLECTION.md`.
